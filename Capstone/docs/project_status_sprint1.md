## 1. Executive Summary

The project applies Organizational Network Analysis (ONA) to identify "silent teams" inside Canon EMEA's Information Management Solutions Professional Services group — sub-teams whose members rarely surface in voluntary community channels and whose hidden support needs therefore go undiagnosed. The deliverable is twofold: a network topology visualization map exposing isolated clusters and over-relied-upon central hubs, and a predictive model that flags individuals at high risk of becoming isolated in the future. Strict GDPR posture forbids using real production communications data, so all analysis runs on a reproducible synthetic dataset generated under documented behavioral archetypes. Sprint 1 (the data-foundation sprint) is complete: schema is frozen, 300-node / 1042-edge mock data is generated and quality-checked, an initial topology prototype is produced, and a sponsor review pack is delivered. Sprint 2 will compute centrality metrics, define the Isolation Score, and produce the first management-facing shortlist of silent individuals/teams.

## 3. Methodological Framework

The analytical stack draws on three established traditions:

- **Organizational Network Analysis (ONA), Cross & Parker (2004).** Two relational attributes are captured *on every observed help-seeking edge*: an *Awareness Score* (does the seeker understand the target's skills?) and an *Energy Score* (is the interaction energizing or de-energizing?). These are edge-level properties, not separate interaction types.
- **Strength of Weak Ties, Granovetter (1973).** Tie strength is mapped from self-reported interaction frequency: Daily=4, Weekly=3 (strong ties); Monthly=2, Rarely=1 (weak ties). Weak ties function as bridges between clusters; their *absence* is treated as a structural root cause of silent silos.
- **Power-User / Broker / Failure analyses.** Standard customer-journey-style analyses adapted to an internal employee network: power users become central hubs, brokers bridge otherwise-unconnected teams, failure analysis investigates silent islands.

**Four behavioral archetypes** are explicit categorical labels in the synthetic data, used both for generation and for ground-truth validation:

| Archetype | Behavior signature |
| :-- | :-- |
| `balanced` | Default; mixed inbound/outbound, mid-frequency, multiple targets |
| `hub` | Very high inbound, broad in-degree from many seekers |
| `broker` | Cross-team soft (business-coordination) ties; bridges otherwise-disconnected clusters |
| `island` | Near-zero outbound; extreme target concentration; weak-bridge deficit |

**Isolation Score** is a composite risk index computed from edges (and optionally node covariates), combining four sub-signals — *OutboundScarcity*, *WeakWeightShare*, *TargetConcentration*, *WeakBridgeDeficit* — with tunable weights. A binary `Isolation_Risk_Flag` is then derived from a threshold on this score and serves as the supervised target *y* for the Sprint 3 predictive model (Logistic Regression for interpretability + Random Forest for non-linear interactions; AUC, Brier Score, and Confusion Matrix for evaluation; 80/20 holdout + 5-fold CV).

For exact formulas, derived feature definitions, and the field-level rationale, see `mock_codebook.md`. For exact survey item wording (Sections A through J), see `mock_survey.md`.

## 4. Data Structure — Two-Table Schema

Synthetic data is delivered as two CSV tables linked on `EMP_ID`.

### 4.1 `mock_data_nodes.csv` — one row per employee (300 rows)

| Group | Variables | Scale / Domain |
| :-- | :-- | :-- |
| Identifiers / metadata | `EMP_ID`, `Seniority` (Junior/Mid-level/Senior), `Team` (6 functional teams), `Years_Exp` (integer), `Profile_Type` (balanced/hub/broker/island — simulation label) | Categorical / integer |
| Section A — Hard / Tech | `A1_PostgreSQL` … `A8_API`, `A9_TechConsult` | 0–5 behavioral frequency band |
| Section B — Hard / Language | `B1_English`, `B2_German`, `B3_French`, `B4_OtherLang` | 0–5 |
| Section C — Soft / Business engagement | `C1_ClientMeetings`, `C2_ScopingSessions`, `C3_IndustryAdvice` | 0–5 |
| Section D — Soft / Knowledge sharing | `D1_KnowledgeSessions`, `D2_MentoringCount`, `D3_CrossTeamContrib` | 0–5 |
| Section E — Soft / Leadership | `E1_TeamLeadCount`, `E2_EscalationsToMe`, `E3_UnblockCount` | 0–5 |
| Section F — Soft / Problem solving | `F1_IncidentsCalled`, `F2_ProblemConsults`, `F3_InnovationsAdopted` | 0–5 |
| Section G — Soft / Cross-cultural | `G1_MultiCountryProj`, `G2_CulturalBridging` | 0–5 |
| Section H — Soft / Communication | `H1_StakeholderExplain`, `H2_DocsAuthored`, `H3_PresentationsGiven` | 0–5 |
| Target ($y$) | `Isolation_Risk_Flag` | Binary 0/1, derived from Isolation Score |

The 0–5 bands are *behavioral frequencies* (counts of events in a defined recall window), not self-rated skill levels. This is a deliberate measurement-theory choice to capture revealed competence rather than self-perception.

### 4.2 `mock_data_edges.csv` — one row per directed help-seeking nomination (1042 rows)

| Variable | Domain | Note |
| :-- | :-- | :-- |
| `Source_EMP_ID` | EMP_* | The respondent who *seeks* help (tail of edge) |
| `Target_EMP_ID` | EMP_* | The colleague *nominated* (head of edge) |
| `Interaction_Type` | `Hard` / `Soft` | Hard = technical help-seeking; Soft = business coordination help-seeking |
| `Interaction_Frequency` | `Daily` / `Weekly` / `Monthly` / `Rarely` | Tie strength; mapped to weights 4/3/2/1 |
| `Awareness_Score` | 1–5 | Cross & Parker latent knowledge awareness on this tie |
| `Energy_Score` | 1–5 | Relational energy on this tie |
| `Nomination_Rank` | 1, 2, or 3 | Order within the same `(Source_EMP_ID, Interaction_Type)` |

Each respondent may nominate **up to 3** colleagues per `Interaction_Type` (Hard, Soft). A respondent who genuinely has no one to seek help from leaves slots blank — that absence is itself an analytical signal for silent islands. No communications content, no message metadata, and no geolocation are stored, by GDPR design.

For field-by-field descriptions, derived feature recipes (Hard_Score / Soft_Score / Competence_Score etc.), and the formal Isolation Score definition, see `mock_codebook.md`. For survey item text including the exact wording of the Awareness and Energy prompts, see `mock_survey.md`.

| Aspect | Value |
| :-- | :-- |
| Generator | `src/generate_assets.py` (cross-sprint reusable, ~450 LOC, no heavy ML deps) |
| Seed | `5228` (any rerun with the same seed reproduces identical CSVs bit-for-bit) |
| Volume | 300 nodes / 1042 edges |
| Profile mix | balanced 222 / island 41 / broker 29 / hub 8 |
| Edge type mix | Hard 490 / Soft 552 |
| Frequency mix | Daily 240 / Weekly 409 / Monthly 259 / Rarely 134 |
| Generation logic | Per-node attributes are drawn from band distributions tuned by archetype; edges are sampled with archetype-conditioned target preferences (hubs attract many inbound nominations, brokers issue cross-team Soft nominations, islands have near-zero outbound, balanced employees draw uniformly from peers) |

The generator deliberately avoids matplotlib / networkx for Sprint 1 — only `csv`, `random`, `pathlib`, `collections`, and Pillow (for prototype PNG rendering) are imported — so the data path is reproducible on a bare Python install.

Because the four archetype labels travel with the data (`Profile_Type`), they double as **scenario-injection ground truth**: Sprint 2's Isolation Score must rank the 41 `island` archetypes high; Sprint 3's classifier must learn to flag them from attributes alone (without seeing `Profile_Type`).

What the pipeline does **not** do yet (intentional Sprint 2+ scope):

- No **betweenness centrality** computation.
- No **Isolation Score** calculation, no `Isolation_Risk_Flag` derivation in production CSV (column exists in nodes table but is not yet algorithmically populated from edges).
- No **community detection** (Louvain / Leiden) or **role discovery**.
- No **predictive model** training or evaluation.
- No **interactive / dynamic visualization** (e.g., D3, PyVis, Gephi export). Sprint 1 produces static PNG only.
- No **counter-metric instrumentation** for the eventual model.

## 11. Governance & Audit Trail

Three project-management practices are baked into the repo so Sprint 2 work and the eventual capstone defense rest on a defensible foundation:

1. **PID is immutable.** The signed Project Initiation Document is preserved as-is in `docs/PID.md`. Any divergence is *registered, not silently absorbed*.
2. **Deviations are explicitly logged in `docs/PID_delta_log.md`.** Each entry records the PID phrase, the actual implementation, the reason (GDPR, sponsor agreement, etc.), and an explicit impact assessment against Key Problem / Objective / Primary Deliverable. A separate "big-picture consistency self-check" table at the bottom of that file flags whether each high-level PID commitment is still on-track.
3. **Schema and structural evolution is tracked in `docs/CHANGELOG.md`.** Versions follow a SemVer-spirit convention: v0.1.0 (legacy single-table) → v1.0.0 (Sprint 1 double-table freeze) → v1.1.0 (April 2026 directory restructure).
4. **Obsolete files are archived, not deleted.** The `_archive/` directory has a strict treatment policy in its `README.md`: archived items are immutable, never read by any active script, and each subdirectory corresponds to one major schema or structural change.
