# AI-Generated Survey Respondents: A Responsible Student Guide

## Purpose of this guide
You may encounter projects where you want an AI model to fill out a survey as simulated people, users, customers, stakeholders, or agentic personas. This can be useful, but it has to be handled carefully. AI-generated survey data can help you test whether a survey instrument behaves coherently. It can help you explore scenarios, debug confusing questions, and generate hypotheses. It should not be treated as a substitute for real human survey data unless it is validated against real respondents.

**Good claim:**
These are controlled synthetic responses generated by persona-conditioned AI agents. The analysis evaluates whether the simulated responses show coherent and interpretable structure.

**Bad claim:**
This survey shows what real people believe.

## What synthetic survey data is useful for

**Good uses:**
* Survey pretesting
* Debugging unclear or redundant questions
* Checking whether intended constructs appear in the data
* Exploring hypothetical user or stakeholder segments
* Generating hypotheses before collecting human data
* Teaching measurement, reliability, factor analysis, and validation
* Comparing possible scenarios before conducting real research

**Weak or inappropriate uses:**
* Estimating real public opinion
* Making claims about market demand
* Replacing human subjects in serious empirical research
* Making policy recommendations without human validation
* Reporting population-level effects
* Treating p-values as if they came from a real probability sample

### Domain sensitivity matters
Not all simulated surveys carry the same risk. Lower-risk examples include classroom exercises, early product ideation, survey debugging, and internal scenario exploration. 

Higher-risk examples include political attitudes, health, hiring, education assessment, marginalized populations, legal decisions, financial decisions, or policy claims. The more consequential the claim, the more human validation is required.

Synthetic data may be acceptable for asking, "Does this instrument behave coherently in a controlled simulation?" It is usually not enough for asking, "What does this population believe?"
*(Synthetic data is simulated evidence, not population evidence.)*

## Responsible generation workflow

### Step 1: Define the survey clearly
Before generating any responses, make sure each survey item has a clear purpose. For each item, ask:
* What construct is this item supposed to measure?
* Is the wording clear?
* Is the response scale appropriate?
* Are there reverse-coded items?
* Are there multiple items per construct?
* Could a respondent reasonably answer this question from the persona information provided?

**Example constructs:**
* AI familiarity
* Trust in institutions
* Privacy concern
* Risk tolerance
* Adoption intention
* Perceived usefulness
* Price sensitivity
* Technical confidence

A survey with no clear constructs is hard to validate, whether respondents are human or synthetic.

### Step 2: Build a respondent frame
Do not ask the model to simply "pretend to be 1,000 people." If you need N=1,000, first create a structured respondent frame with 1,000 rows. Then generate one response per row.

A respondent frame is a table of synthetic respondents. Each row represents one simulated person or agent.

**Example fields:**
* respondent_id
* age_band
* country_or_region
* education_level
* occupation
* domain_experience
* income_band
* technical_familiarity
* risk_tolerance
* institutional_trust
* privacy_concern
* price_sensitivity
* response_style

**Example synthetic respondent:**

    {
      "respondent_id": "R0421",
      "demographics": {
        "age_band": "35-44",
        "country_or_region": "Austria"
      },
      "education_level": "masters",
      "occupation": "mid-level analytics manager",
      "latent_traits": {
        "technical_familiarity": 0.74,
        "risk_tolerance": 0.62,
        "institutional_trust": 0.41,
        "privacy_concern": 8.68,
        "price_sensitivity": 0.58
      },
      "response_style": {
        "acquiescence": 0.20,
        "uncertainty_tolerance": 0.78,
        "extreme_response_tendency": 0.10
      }
    }

**Avoid unrealistic independence**
Do not independently randomize every persona attribute if that creates implausible combinations. Age, income, education, occupation, country, technical experience, and institutional trust may be correlated in real populations.

**Better options:**
* Use empirical marginals or real benchmark data when available.
* Use plausible constraints, such as age ranges by occupation level.
* Use scenario-based segments if the goal is exploration rather than population approximation. Explicitly state when the respondent frame is hypothetical.

### Step 3: Separate persona creation from survey answering

**Weak approach:**
Pretend to be 500 different people and answer this survey.

**Better approach:**
1. Create or load a respondent profile.
2. Pass that profile into the model.
3. Ask the model to answer the survey as that respondent.
4. Store the profile and the response together.

This makes the simulation auditable. You can later inspect whether responses actually reflect persona attributes.

### Step 4: Use structured prompting

**Useful prompt pattern:**

    You are answering as the synthetic respondent below. Treat the profile as a set of tendencies, not deterministic rules. Answer like a real person: mostly consistent, but not perfectly mechanical. Do not optimize for pleasing the researcher. Return only valid JSON.
    
    Respondent profile:
    {persona_json}
    
    Survey:
    {survey_items}

**Recommended output format:**

    {
      "respondent_id": "R0421",
      "answers": [
        {"item_id": "001", "response": 4},
        {"item_id": "002", "response": 2}
      ]
    }

During development, you may optionally ask for a short rationale. Remove rationales from the final quantitative dataset unless you are explicitly analyzing explanations.

### Step 5: Add variability deliberately
Human respondents are not perfectly consistent. Synthetic respondents should not be perfectly consistent either. Use several sources of variability:
* Different latent traits across respondents
* Different response styles
* Randomized item order
* Multiple model runs
* Multiple random seeds, if available
* Multiple models, if feasible
* Slight prompt variations as robustness checks

If your survey is long, avoid presenting 100 items in one huge block without checks. Long prompts can create response drift. Consider section-by-section answering, randomized item order, or consistency checks across repeated runs.

Be suspicious if synthetic data looks too clean. Perfect reliability, perfect factor structure, or perfectly aligned subgroup differences may indicate that the model is performing the researcher's theory rather than simulating plausible respondents.

### Step 6: Store full provenance
For every synthetic response, store enough information to reproduce and audit the result.

**At minimum, store:**
* respondent_id
* persona_json
* survey_version
* item_order
* model_name
* model_version
* prompt_version
* temperature
* top_p
* timestamp
* raw_output
* parsed_output
* validation_errors
* retry_count

This matters because AI-generated data can be sensitive to prompts, model versions, and generation settings.

## Practical guidance before scaling

### Sample size rules of thumb
Synthetic N does not create real-world representativeness. A larger synthetic sample mostly reduces simulation noise; it does not solve the problem that the respondents are not human.

| Goal | Rough synthetic N |
| :--- | :--- |
| Prompt and pipeline debugging | 20-50 |
| Initial survey behavior check | 100-200 |
| Known-groups comparisons | 200-500+ |
| Factor analysis | 300-500+ minimum, preferably more |
| Robustness across models, prompts, or seeds | Repeat smaller batches first |

Start small. Do not generate 10,000 responses before you know your schema, parser, prompts, and validation checks work.

### Cost, time, and access
Large simulations can be expensive and slow, especially if each response includes long rationales or very large persona profiles.

**Practical advice:**
* Start with 100-200 synthetic respondents to test the pipeline.
* Use shorter prompts once the method is stable.
* Avoid rationales in the final full-scale generation unless needed.
* Consider cheaper or open models for pipeline testing.
* Use commercial models when quality, instruction following, or JSON reliability matters.
* Use rule-based simulation when the goal is only to test data processing or plotting code.

## Minimum viable validation vs. advanced validation
Students often see a long list of statistical methods and do not know where to start. Use this split.

### Minimum viable validation
At minimum, do all five:
1. Compute reliability for each multi-item construct.
2. Inspect item distributions.
3. Run at least one known-groups test based on persona attributes.
4. Repeat the simulation with one alternate prompt, item order, or seed.
5. State clearly that the data is simulated and not population evidence.

This is the smallest defensible validation stack for a class project.

### Advanced validation
Use these when the project is more serious, the survey has multiple constructs, or the synthetic data will support an important claim:
* Exploratory factor analysis
* Confirmatory factor analysis
* Parallel analysis
* Structural equation models or path models
* Measurement invariance across model, persona group, or item order
* Human benchmark comparison
* Multiple-model comparison
* Distributional divergence metrics
* Bootstrap or repeated-run stability checks

## Statistical evidence for coherence
The goal is not to prove that the data is real. The goal is to evaluate whether the synthetic data has coherent, interpretable structure.

### 1. Item-level diagnostics
For each item, compute: mean, standard deviation, median, response frequencies, skew, kurtosis, entropy, missing or invalid response rate.

**Red flags:**
* Everyone gives the same answer.
* Almost everyone chooses the middle option.
* Almost everyone agrees.
* There is very little variance.
* Distributions are suspiciously smooth.
* Different persona groups look almost identical.

**Possible tools:** chi-square goodness-of-fit tests, Kolmogorov-Smirnov tests, Jensen-Shannon divergence, Wasserstein distance, entropy comparison.

### 2. Reliability of multi-item constructs
If several questions are intended to measure the same construct, test whether they hang together.

**Common measures:** Cronbach's alpha, McDonald's omega, item-total correlations, alpha-if-item-deleted, inter-item correlation matrix.

**Good signs:**
* Items intended to measure the same construct correlate with each other.
* Reverse-coded items behave in the expected direction.
* Alpha or omega is in a plausible range, often around 0.70 to 0.90.

**Suspicious signs:**
* Reliability is extremely high, for example alpha above 0.95.
* Every item correlates strongly with every other item.
* Reverse-coded items are too perfectly mirrored.
* The data looks more internally consistent than real human data normally would.

High reliability is not automatically good. With AI-generated data, extremely high reliability may indicate a model artifact.

### 3. Factor structure
Factor analysis helps test whether the survey items group into the constructs you expected.

**Useful methods:** exploratory factor analysis, parallel analysis, confirmatory factor analysis, principal component analysis as a diagnostic.

**Ask:**
* Do items intended to measure the same construct load together?
* Are different constructs distinguishable?
* Do reverse-coded items load in the expected direction?
* Is there one giant "general positivity" factor?
* Does the factor structure remain stable across models, seeds, or item orders?

For confirmatory factor analysis, inspect: CFI, TLI, RMSEA, SRMR, standardized factor loadings, residual correlations.

A coherent synthetic survey should show interpretable structure, but not unrealistically perfect structure.

### 4. Known-groups validity
Known-groups validity asks whether groups that should differ actually do differ. Before generating responses, write down expected relationships.

**Examples:**
* High AI familiarity -> higher AI confidence
* High privacy concern -> lower willingness to share data
* Executives -> more strategic-risk concern
* Technical workers -> more operational confidence
* Price-sensitive personas -> higher cost-barrier ratings

**Test with:** t-tests, ANOVA, Kruskal-Wallis tests, ordinal logistic regression, Linear regression with robust standard errors, multilevel models, effect sizes such as Cohen's d or eta-squared.

**Good evidence:** Effects are in the expected direction. Effect sizes are plausible. Results are not entirely dependent on one model or one prompt.

**Red flags:**
* Every hypothesized relationship is extremely strong.
* The model produces stereotypes rather than nuanced variation.
* Small persona wording changes produce large result changes.
* Different models produce completely different conclusions.

### 5. Nomological validity
Nomological validity asks whether constructs relate to each other in theoretically sensible ways.

**Example expected relationships:**
* AI familiarity -> perceived usefulness -> adoption intention
* Privacy concern -> resistance to data sharing
* Institutional trust -> comfort with centralized AI governance
* Risk tolerance -> willingness to experiment
* Technical confidence -> lower perceived difficulty

**Useful methods:** correlation matrices, partial correlations, path models, structural equation models, regularized network models.

**Good evidence:** Related constructs correlate in expected directions. Unrelated constructs remain distinguishable. Relationships are meaningful but not perfect.

**Red flags:** Everything correlates strongly with everything. One generic "positive attitude" dimension explains the whole survey. The data reflects obvious prompt cues more than plausible psychology or behavior.

### 6. Robustness checks
A coherent simulation should not depend on one exact prompt or one exact model run.

**Repeat the simulation across:** different random seeds, different item orders, different prompt phrasings, different model settings, different AI models (if available), different batches or generation dates.

**Then compare:** item means, item distributions, scale scores, factor structure, regression coefficients, subgroup differences, construct correlations.

**Possible robustness statistics:** intraclass correlation coefficient, test-retest correlations, mean absolute difference, coefficient stability, bootstrap confidence intervals, measurement invariance tests.

If the main findings only appear under one prompt and one model, the evidence is weak.

### Model and instruction sensitivity
Different models have different default survey personalities. Some may be more agreeable, cautious, polite, Western-centric, middle-of-the-scale, extreme, or over-coherent than others.

**At minimum, test one sensitivity:**
* Same personas, different item order
* Same personas, slightly different instruction wording
* Same personas, different temperature
* Same personas, different model, if available

**Example instruction sensitivity test:**
* Prompt A: Answer like a real person.
* Prompt B: Answer as a busy professional responding quickly.
* Prompt C: Answer carefully but do not overthink.

If aggregate results change drastically across these small changes, report that instability and avoid strong substantive claims.

### Comparing synthetic data with human benchmark data
The strongest design combines synthetic simulation with at least a small human benchmark. Even 50-200 human responses can help compare: item means, item variances, rank order of item means, response distributions, construct reliabilities, factor structure, construct correlations, known-groups effects.

**Possible quantitative comparisons:** Cohen's d for mean differences, variance ratios, Spearman correlation of item means, Jensen-Shannon divergence for categorical distributions, Wasserstein distance for ordinal or continuous approximations, predictive validity comparison (if there is an outcome variable).

**Useful heuristics:**
* Small mean differences are better than large mean differences.
* Similar rank ordering of items is often more important than exact equality.
* Similar construct correlations are stronger evidence than similar item means alone.

A human benchmark does not make the synthetic sample representative unless the human benchmark is itself representative.

**With a benchmark, a careful claim is:**
> The synthetic survey is internally coherent and approximates selected patterns observed in a small human benchmark, but it should not be treated as representative human evidence.

## Troubleshooting common problems
* **Reliability is too high:** the model may be over-optimizing for consistency. Try adding response-style variation, reducing "be consistent" language, and varying item order.
* **Reliability is too low:** items may be unclear or personas may be under-specified. Review item wording, define constructs better, and enrich persona traits.
* **One giant factor dominates:** this may reflect general positivity, acquiescence, or a prompt artifact. Add reverse-coded items, add response-style traits, and test alternate prompts.
* **Persona attributes do not predict answers:** the traits may not be salient or connected to the items. Strengthen profile variables, pre-register expected effects, and test prompt sensitivity.
* **Models disagree strongly:** treat this as a model-specific artifact until proven otherwise. Report the disagreement, avoid strong claims, and compare distributions and factor structure.
* **Responses are too stereotyped:** persona labels may be too broad or loaded. Use behavioral details instead of identity shortcuts and reduce demographic caricature.
* **Too many invalid JSON outputs:** the prompt or schema is too loose. Use a stricter schema, validate outputs, and retry only with logged provenance.
* **Results change when item order changes:** order effects or prompt drift may be driving the results. Randomize order, answer in sections, and report order sensitivity.

## Implementation hints
You do not need to master every method before starting. Use the simplest tools that answer your validation question.

**Python libraries that may help:** pandas, numpy, scipy, statsmodels, pingouin, factor_analyzer, semopy, scikit-learn

**R libraries that may help:** psych, lavaan, lme4, survey, ordinal

**Example task-to-tool mapping:**

| Task | Python options | R options |
| :--- | :--- | :--- |
| Item summaries | pandas, scipy | base R, dplyr |
| Cronbach's alpha | pingouin | psych |
| Factor analysis | factor_analyzer | psych, lavaan |
| Regression | statsmodels | lm, glm, lme4 |
| Distribution distances | scipy, scikit-learn | philentropy, transport |
| SEM/path models | semopy | lavaan |

Do not use advanced methods as decoration. Use them only when they answer a clear validation question.

## How to write up the findings
Use careful, accurate language.

**Strong language:**
* The synthetic respondents produced internally coherent survey patterns.
* The intended constructs showed reasonable reliability and factor structure.
* Persona attributes predicted responses in expected directions.
* Results were broadly stable across item order randomization and repeated model runs.
* The simulation is useful for instrument testing and scenario exploration.

**Avoid overclaiming:**
* This proves what real people believe.
* The sample is representative.
* The p-values show real population effects.
* AI respondents are equivalent to human respondents.
* This replaces human data collection.

## Final checklist for students
Before presenting AI-generated survey data, make sure you can answer yes to the following:
* [ ] Did I define a clear survey purpose?
* [ ] Did I define constructs before generating responses?
* [ ] Did I create explicit respondent personas or a respondent frame?
* [ ] Did I avoid unrealistic independent randomization of persona attributes?
* [ ] Did I separate persona creation from survey answering?
* [ ] Did I store prompts, model settings, and raw outputs?
* [ ] Did I check item-level distributions?
* [ ] Did I test reliability for multi-item scales?
* [ ] Did I run at least one known-groups test?
* [ ] Did I run at least one robustness or sensitivity check?
* [ ] Did I avoid claiming that synthetic responses represent real people?
* [ ] Did I clearly describe the data as simulated?

**For advanced projects, also ask:**
* [ ] Did I examine factor structure?
* [ ] Did I compare multiple models or prompt variants?
* [ ] Did I test whether construct relationships made theoretical sense?
* [ ] Did I compare with human benchmark data, if available?
* [ ] Did I explain failure modes or instability honestly?

## Bottom line
AI-generated survey respondents can be useful for learning, testing, and exploration. They can help you examine whether a survey has coherent internal structure and how different hypothetical personas might respond. 

But synthetic respondents are not human respondents. Treat the data as simulated evidence, not population evidence.

The responsible question is not: 
*Did the AI survey prove something about the world?*

The responsible question is: 
*Did this controlled simulation produce coherent, interpretable, and robust patterns that are useful for survey design, theory testing, or hypothesis generation?*
